## Answer

# VERDICT

**All three of your readings are correct, and I verified each against the code and the vendored configs rather than your description.** Your framing is the right one to take to the planner: this is a failure to implement A5, not a change to it, and the fix moves rung 2 *toward* published practice.

**But I disagree with your leaning on the fix.** Option (c) cannot work for rung 2a, because R29 restricted 2a's positional fallback to the *pre-commitment* span, which is empty on exactly these texts. You would end up with two different repairs. I recommend (a), scoped by the `answer_type` the config already declares.

## Q1 — reading 2 is correct; the ordering is the defect

**Rule order** (`extract.py:388-403`), verified:

```
boxed → commitment_phrase → hash_marker → [last_option_letter if MC] → [last_number if numeric]
```

The loop `return`s on the first rule producing a non-empty normalised value, so **when `commitment_phrase` matches, the flexible regex never runs.** `_extract_last_number` is `_apply_harness_regex(FLEXIBLE_PATTERN, text, group_select=-1)` — that *is* the harness's flexible-extract — and it is dead last.

**The harness regex cannot produce these values.** `vendor/lm-eval-configs/gsm8k/gsm8k.yaml:41` and `gsm8k-cot.yaml:55` both specify `(-?[$0-9.,]{2,})|(-?[0-9]+)` with `group_select: -1`, byte-identical to `FLEXIBLE_PATTERN` at `extract.py:58`. The character classes admit digits, `$`, `.`, `,` and a leading `-` only — **no letter is reachable**. So `'5 days'`, `'84 grains'` and `'230 miles for each train'` did not come from published practice. Reading 1 confirmed.

**Would the flexible regex alone return the gold?** Analytically yes on all three:

| text | alternative that fires | matches | `group_select=-1` |
|---|---|---|---|
| `The answer is 5 days. It will take Prince 5 days…` | alt 2 `(-?[0-9]+)` | `5`, `5` | `5` ✓ |
| `The answer is 84 grains.` | alt 1, run of ≥2 class chars | `84` | `84` ✓ |
| `The answer is 230 miles for each train` | alt 1 | `230` | `230` ✓ |

⚠️ **That is analytic, not executed** — arbitrary `python -c` is refused in this session, so I could only run `pytest` and `ruff`. It is the empirical claim your entire fix rests on, so pin it as a test before you write the fix, not after.

So state it exactly as you have: `commitment_phrase` is ours, it precedes the harness rule, and on this population it returns a strictly worse answer than the harness rule would have. Repairing it moves rung 2 closer to published practice, which is the opposite of what R27.1 forbids.

**One refinement worth having.** `EXECUTOR-TASKS.md:373` lists rung 2's rules as *"last-number-in-string, `\boxed{}`, "answer is X", comma/currency/unit stripping, Minerva `normalize_final_answer`"* — naming last-number **first**. I would not lean on that as a precedence declaration, since it reads as prose. But it does mean the current precedence is not something the registration asked for either, which strengthens your position: neither the ordering nor the missing unit strip is registered behaviour.

**Reading 3 confirmed verbatim.** A5 requires "comma/currency/unit stripping". `normalise_answer` implements comma stripping (`(?<=\d)[,_](?=\d\d\d\b)`) and currency stripping (`.strip("$€£%")`). Unit stripping exists only as `_MINERVA_REMOVE_UNITS`, which matches units **inside `\text{...}` LaTeX wrappers** — a plain-prose `"5 days"` never has one. So one third of a registered triple is absent on every non-LaTeX path.

## Q2 — (a), scoped by `answer_type`. Not (c).

**Why (a) is the defensible ground.** A5 registers unit stripping as part of rung 2. Implementing it is not an invention you have to justify to the planner; it is closing a gap between the registration and the code. That is the strongest position available, and it is the one your own framing already identifies.

**Your objection to (a) is real and is solved by scope, not by abandoning it.** `configs/tasks.yaml` already declares the answer type: `answer_type: numeric` at lines 69, 99, 151 (the three GSM8K configs) and 252, 257 (`multistep_arithmetic_two`, `object_counting`); `answer_type: multiple_choice_letter` at 366; and `format_class: free_form | boolean | multiple_choice` per BBH subtask. Restricting unit stripping to numeric answer types covers the entire 2,068-item class-D population and excludes `word_sorting` and `dyck_languages` by construction, so word-list answers are never touched.

🚨 **But do not extend `NUMERIC_TASKS` to do this.** `extract.py:60-62` hardcodes `NUMERIC_TASKS` and `MULTIPLE_CHOICE_TASKS` as frozensets while `tasks.yaml` declares the same thing as `answer_type`. That is the `HARNESS_UNTIL` shape — a config value retyped in code — which drifted once and became a CRITICAL that zeroed `TRUNC_STOPSEQ` for weeks. If the fix keys on answer type, **read it from the config**, or you plant the identical defect in the identical place.

**Why not (c), and this is the part you have not spotted.** R29 restricted rung 2a's positional fallback to `scope = generation if span is None else generation[:span[0]]` (`extract.py:551`) — the text *before* the commitment phrase. On `"The answer is 5 days. …"` the phrase starts at position 0, so `scope` is `""` and `_extract_last_number("")` returns `None`. So falling through on 2a yields nothing at all; and on texts where the phrase appears later it would return a number from the **reasoning**, which is worse than a unit-suffixed correct answer. (c) therefore fixes rung 2 and either fails or actively harms rung 2a, leaving you with two divergent repairs on rungs that must stay comparable.

There is a second reason to keep the arbiter out of the control flow: (c) makes *which rule fires* depend on whether the value happened to normalise to the task's answer type. Extraction must be a pure, gold-blind function of the generation. Conditioning on the declared answer *type* is fine; conditioning control flow on "did this parse as a number" is one step from conditioning on the gold, and this project's §4.0 discipline is precisely about not letting an outcome influence a measurement path.

**The smallest correct fix.** Teach `normalise_answer` the answer type and, when it is numeric, keep the leading numeric span when the value is a numeric span followed by non-numeric text. `normalise_answer` currently takes only the candidate string, so this means one keyword argument threaded from the four call sites in `extract_permissive` and `extract_permissive_anchored` — defaulting to unknown, so no existing behaviour moves. One function, gold-blind, type-scoped, identical effect on rungs 2 and 2a, last-candidate semantics untouched.

**Reject (b).** It puts numeric parsing inside `commitment_phrase`, duplicating what `normalise_answer` exists for, and needs the same change again in 2a's inline span rule at `:542-548`.

**One thing that is the planner's, not yours.** Whether the repaired rung 2 still counts as "published practice". My reading is that you are inside R27.1: its constraint was on the last-candidate *semantics*, which you are not touching. But prereg §5a's destruction count is about to fall from 2,218 to roughly 150, and per-arm destroyed/recovered ratios with it. A registered number moving by an order of magnitude needs blessing, and §5a's class table (A/B/C/D) will need a fourth class or a restatement.

## Q3 — yes, 2a shares it, and the 4% is the right signature

`_extract_after_first_commitment_phrase` (`:436-459`) and the inline span rule (`:542-548`) both take the span after the phrase, apply the same sentence split `(?<=[0-9A-Za-z\)\}])\.(?:\s|$)`, and hand the result to `normalise_answer`. Identical tail handling to rung 2's. `"The answer is 5 days. It …"` → tail `"5 days"` → unchanged.

The phrase sets differ — `_ANCHOR_PHRASES` drops the bare `"answer:"` header, which was my finding from round 4 — but the **trimming** does not differ at all. So 2,128 against 2,218 is exactly what you would expect from a rung that changed which phrase it anchors on and nothing about how it trims. Your inference is right.

Note the ordering asymmetry while you are in there: 2a is `hash_marker → boxed → first_commitment_phrase → anchored positional`, while 2 is `boxed → commitment_phrase → hash_marker → positional`. Both orderings are justified in their comments (2a puts hash first to coincide with rung 1's `group_select=0`), so this is not a defect — but any fix must be applied to both tail paths, and there are two of them in 2a's file region.

## Q4 — one real over-count in H2; the compliance labels are safe

`normalise_answer` has exactly two consumers outside `extract.py`, both in `scan_trace`:

- `compliance.py:427` — `normalised_gold = normalise_answer(gold)`. Unaffected; gold carries no units.
- `compliance.py:443` — `already_extracted = extracted is not None and normalise_answer(extracted) == normalised_gold`. **This is a real H2 over-count.**

For a class-D item, `normalise_answer("5 days") == "5"` is False, so `already_extracted` is False, so `conservative = (in_final_span or after_marker) and not already_extracted` can be True. H2 then counts the item as *"the gold is in the trace but the extractor did not already have it"* — when the extractor did have it and merely carried a unit. So H2's pre-registered conservative variant is inflated on the same 2,068 items, **in the direction that favours the paper's finding**. Same direction-of-error signature as the destruction rate, and it must be recomputed alongside it. Add it to the blast radius you report to the planner; it is a second registered quantity, not a side effect.

**The compliance labels are fine, and your worry there is unfounded.** `COMMITMENT_RULES` includes `"commitment_phrase"` (`extract.py:81`), so `Extraction.committed` is True for `"5 days"`. `label_compliance` assigns COMPLIANT on `strict.committed`, RECOVERABLE on `permissive.committed`, ABSENT otherwise — all keyed on **committed**, never on **correct**. A unit-suffixed value still evidences that the model committed, which is what the label means. So no item is mislabelled, RECOVERABLE and ABSENT are unaffected, and §1.1's stratum is untouched. The `found`/`committed` split that R26.3 made scorer-independent is doing exactly the job it was designed for, and it is the one thing this census does not contaminate.
