A process killed mid-`with`, or a SageMaker checkpoint sync that copies the file mid-write, leaves an **incomplete deflate stream**. Python's `_GzipReader` raises `EOFError("Compressed file ended before the end-of-stream marker was reached")`. `read_records` catches `json.JSONDecodeError` only.
- **How it fails:** `build_resume_index` propagates `EOFError` → the `CELL_SCRIPT` subprocess dies → `run_one_cell` returns `None` → the unit is marked failed → and it fails identically on **every** resubmit. One cell of a ladder described as "all load-bearing — the ladder is a dose-response" is permanently unresumable without hand-editing the file in S3. `GENERATIONS_ROOT` is the continuously-synced checkpoint prefix, so the mid-sync path needs no kill at all.
- **The test is the second half of this finding.** `tests/test_records.py:211` writes its partial line inside a `with gzip.open(..., "at")` block, which **closes cleanly** — producing a valid member containing an incomplete line. It pins a scenario a killed process does not produce, and passes against the implementation that mishandles the one it does.
- **Confirmed by:** reading only — not executed. I could not run Python to trigger the `EOFError`, and I want to be explicit that the exception type is a mechanism claim from reading CPython's gzip reader, not something I observed. **Verify this one before acting on it** — it is the single finding here most worth ten seconds of `python -c`.
- **Fix:** catch `(json.JSONDecodeError, EOFError, gzip.BadGzipFile, zlib.error)` in `read_records` and `return`. Then change the test to truncate the file on disk (`path.write_bytes(path.read_bytes()[:-20])`) so it exercises the real signature.

## On your four questions

**1. Is `invocation_id` correct?** Yes, and the reasoning holds. Minting per `VLLMRunner` is the right boundary — the divergence you are chasing is across engine loads, and `subprocess`-per-cell means one runner per load, so one id per load. Keeping it out of `JOIN_KEY` is also right: in the key it would make every resumed batch a new identity and destroy the uniqueness constraint. Two K=2 invocations of one item **are** distinguishable (`repeat_idx` 0 vs 1) and joinable (same `item_id`, same file). The design is sound; the defect is that the only existing joiner ignores it (BLOCKER).

One untested property, and it is the load-bearing one: **nothing asserts that two `VLLMRunner`s get different `invocation_id`s.** `test_it_is_minted_per_engine_load_and_stamped_on_records` greps source strings. A behavioural test is feasible on the laptop — `_llm` is lazy, so constructing a runner loads no engine; you need the three `REQUIRED_ENV` vars set and a `cc` on PATH for `preflight`. Assert two runners differ and that the format is `<UTC>-pid<N>-<8 hex>`.

**2. Does the K=2 resume path work? Is there an eleventh cache-key bug there?** **It works, and no — not in the resume path.** I traced all four states:

| state | pass 1 (`repeat_idx=0`) | pass 2 (`repeat_idx=1`) |
|---|---|---|
| fresh | all N pending → writes N | file holds N keys at `repeat_idx=0`; lookup is at `repeat_idx=1` → all N pending → **regenerates** ✓ |
| resumed after dying mid-pass-2 | keys present → 0 pending → skips ✓ | N−M pending → regenerates only the remainder ✓ |

Both indices share one file, but `JOIN_KEY` includes `repeat_idx` and `run_cell:774-777` puts it in the lookup tuple, so they do not collide. The `__k{repeat_idx}` scratch tagging is also correct and was a real catch — without it the second pass would have clobbered the first's counts.

Two caveats worth recording rather than fixing:

- **Per-item resume means a K=2 pass can straddle two engine loads.** If the job dies mid-pass-2, that cell's `repeat_idx=1` records carry *two* `invocation_id`s and two batch compositions. It inflates the measured floor rather than shrinking it, so it is conservative for class-3 admissibility — but the reported quantity is then not purely invocation noise. **`invocation_id` is exactly what makes this detectable**, which is the field earning its place. Add an assertion when you fit §9f: one distinct `invocation_id` per `(cell_id, repeat_idx)`, or report the cell separately.
- **`max_num_seqs` is still not in the reference/pilot/template resume key.** `decoding_fingerprint()` is called from **`sm_determinism.py` only** — I grepped every call site. So bumping `DECODING_VERSION` to 3 and adding `max_num_seqs` did **not** protect the generation stages. The comment at `generate.py:118-122` names those three stages as the vulnerable ones (*"no batch size anywhere… precisely the stages whose output feeds the paper's deltas"*) and then leaves them vulnerable — it reads as a fix that landed and did not. Live risk: `main-v1` runs at 32, the freeze later moves, someone resubmits `reference`, and every cell is skipped as already-written. That is the ninth instance's exact failure mode, still open for the paper's primary artifact. I did not raise this to MAJOR because it is out of your stated scope and pre-existing, but it is the thing I would fix next: append `decoding_fingerprint(spec)` to the `run_id` or the `cell_path` for the generation stages, and correct that comment either way.

**3. Are the new tests pinning behaviour or spelling?** Mostly spelling — which is partly legitimate here (the "is it forwarded" idiom is this project's established answer to declared-but-unenforced) but is weaker than you may think. Concretely:

- **Legitimate as-is:** `test_repeat_index_reaches_the_cell_payload`, `test_it_does_NOT_derive_the_level_from_the_sweep` (negative anchors are the strongest form of this idiom), `test_prereg_and_code_agree_on_the_count` (a cross-document pin, and the prereg stabilises at freeze).
- **You found one; there are three more of the same kind.** `test_the_frozen_getter_still_fails_closed` is the worst — it would pass against a gutted implementation (MINOR 11). `test_scratch_paths_distinguish_the_two_invocations` asserts the literal f-string `'f"__k{repeat_idx}" if repeat_idx else ""'`; behaviourally testable by monkeypatching `subprocess.run` and asserting the two payload paths differ. `test_it_is_minted_per_engine_load_and_stamped_on_records` greps `__init__` and misses the one property that matters (uniqueness). `test_schema_version_was_bumped` asserts `!= "1.0.0"`, which `"0.0.1"` satisfies — harmless tripwire, but pin `>= (1,1,0)` if you want it to mean something.
- **The largest gap is not a fragile test, it is an absent one: no test anywhere calls `run_cell`.** I grepped `tests/` — four matches, all inside docstrings or source-string assertions. The `pending` filter is the code your whole K=2 design rests on, it is pure Python needing no GPU, and it has zero behavioural coverage. A fake runner (`.spec`, `.hardware`, `.invocation_id`, `.generate()` returning canned dicts) plus `tmp_path` would pin all four states in the table above in about thirty lines. Given ten prior instances of this bug family, that is the highest-value test in the repo right now.
