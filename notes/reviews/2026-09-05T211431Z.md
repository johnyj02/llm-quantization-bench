## MODERATE 2 — the label and the cap are coupled by convention, not by construction

`sm_pilot.py:275` and `:279`, inside `CELL_SCRIPT`:


The threading itself is correct end to end, and I traced it: `sm_sweep` → `run_one_cell(..., budget_level=level)` → payload → `CELL_SCRIPT` → `run_cell`. `run_id` is correctly the caller's (`sm_reference.py:236`, `cell.get("run_id", RUN_ID)`), so the sweep writes under `sweep-v1` and not `main-v1`. ## MODERATE 3 — the 4x/BBH path is unexercised, and prompt + 4096 against `max_model_len=8192` is unverified

The smoke ran `gsm8k_cot` at 2x, whose cap is 512. It therefore could not have exercised: BBH at all, the 4,096 cap, `bf16` or `awq-4bit`, Llama's or Phi's tokenizer, or the per-subtask BBH config path where `max_gen_toks` is resolved from `tasks["bbh"]` rather than from a flat task entry.

On your specific worry: `EngineSpec.max_model_len = 8192`, so a BBH prompt would have to exceed **4,096 tokens** for `prompt + 4x cap` to overflow. A 3-shot BBH CoT block is normally well under 2,000, so the headroom is roughly 2× and the risk is low — **but I could not verify it.** Reading the stored `n_prompt_tokens` needed a `gzcat`/`zgrep` pipeline and `peek_generations.py`, all of which were refused in this session, so I have no measured number for you and I am not going to assert one.

What I can tell you is that the check is free and the data is already on disk. `main-v1` ran BBH at 1x on **prefix-nested supersets of exactly these items**, and every record carries `n_prompt_tokens`. So the honest guard is a local preflight, not a GPU trip:

> For each `(task, subtask)` in `sweep_plan`, read `max(n_prompt_tokens)` from the corresponding `main-v1` cell file and refuse if `max_prompt + tasks[task]["max_gen_toks"][level] > max_model_len`.

That belongs in `main()`'s existing refusal block at `:114-129`, which already fails closed on config divergence. It turns an unknown into a printed number before a single token is generated.

⚠️ **And on the failure mode if it does overflow: I do not know whether vLLM 0.26 raises or silently clamps `max_tokens` to the remaining context, and it is version-specific.** A silent clamp is the bad outcome, because it produces a cell labelled 4x whose effective cap is smaller — the same class as the defect the build guarded, arriving by a different route. `read_back_engine_state` records `max_num_seqs` and `num_gpu_blocks` but nothing about per-request clamping, so the run would not report it. ## Q4 — the records are joinable; nothing can currently join them

The schema side is clean. `run_cell` populates `until_applied`, `stop_string_hit` and `n_gen_tokens_scored` (`generate.py:1005-1009`), computed at generation time by `_scored_tokens` with the engine's own tokenizer and a documented fallback to the full count when it is unavailable. Because `sm_sweep` goes through the same `CELL_SCRIPT` → `run_cell`, sweep records carry these **identically to reference records** — same writer, same fields, so §5b.1's scored length is available at all three levels. The nesting also holds: `_select_docs` takes a deterministic prefix, so the sweep's 500 GSM8K items and 150-per-subtask BBH items are prefixes of the reference's 1,319 and 150/250.

**The gap is downstream, and it is real.** `JOIN_KEY[0]` is `run_id`, so a 1x record and a 2x record never share a join key — correct, since they are different measurements. But H1's three-point curve needs a join on `(cell_id, task, subtask, item_id)` **across** `run_id` and `budget_level`, and:

- `analyze_run.py` takes a single `--run-id` and reads one directory (`artifacts/generations/<run-id>`), so it cannot see both runs.
- There is no H1 analysis module at all.

So the 1x level will not silently drop — it will simply be unreachable, and H1 will have two points until someone writes the cross-run reader. **Build it before the job, not after.** The reason is not convenience: if the join reveals that a `(cell_id, task, subtask, item_id)` key does not in fact match across runs (a tokenizer change, a limit that is not prefix-nested for one subtask, a `template_level` mismatch), you want to know while regenerating is still a 12-hour job rather than after the queue slot is spent. A dry-run join against `main-v1` alone plus `sweep-v1-smoke` would surface that today at zero cost.
