## Q1 (correctness) and the truncation-design challenge you asked for

**Keep the flag and keep the defaults.** Your reasoning is right and I want to be unambiguous: a short cell silently scored gives every rate a wrong denominator, while on the resume path the recovered prefix is precisely what should be skipped. Strict-for-scoring / tolerant-for-resume is the correct asymmetry, the docstring argues it well, and making both strict would have made a killed job unresumable — which is the worse failure on a one-slot account.

Two real gaps, neither fatal:

- **It is a generator, so the guarantee only holds for callers that consume to exhaustion.** The `raise` fires lazily, mid-iteration. `score_pilot.read_records` builds a full list, so it is protected ✓ (and I verified it now delegates — `score_pilot.py:110` — so the strict default does reach the scoring path, which was my main worry). But `assert_cell_reusable` pulls only the first record, so it never reaches the EOFError and `tolerate_truncation=True` there is inert — harmless, but it *documents* a tolerance that is never exercised, which will read as meaningful to the next person. A one-line comment saying so would be honest.
- **Gap 6 above is the substantive one.** The flag guards one of two routes to the same wrong denominator. Make the JSONDecodeError path respect `tolerate_truncation` too, and count it — a corrupt line and a truncated member are the same event class from the consumer's point of view.

Everything else in the fixes checks out: `until: list[str] | None = None` sits before `schema_version` with all trailing fields defaulted, so no positional construction breaks; `list(until)` creates a fresh list per record so there is no aliasing; the union fallback keeps the pre-existing `"Q"`/`"\n\n"` tests valid rather than silently inverting them; and the new tests at `test_compliance.py:368-382` pin the per-level distinction in both directions, which is the assertion whose absence let B1 through.

## Q2 — is `until` enough to make the artifact self-classifying?

## Q3 — the numeric `stop_reason`, and does it affect anything reported?

**Nothing already reported is wrong.** Both routes return `COMPLETE`, so `trunc_stopseq_rate` and `trunc_budget_rate` are unchanged and your re-scored 16.0% / 48.7% stand. Also note `committed` short-circuits at line 209 *before* the EOS check, so the only numeric-id records that even reach the fallthrough are the uncommitted ones — a subset of the 1,699, and worth measuring rather than assuming.

**Do not add `"32007"` and `"151643"` to `_EOS_STOP_REASONS`.** Model-specific magic numbers in a scorer is how `HARNESS_UNTIL` drifted; you would be fixing the instance and keeping the class.

The principled fix is two parts:

1. **Stop collapsing the type at the source.** `generate.py:734-738`'s `_normalise_stop_reason` does `str(stop_reason)`, which destroys the distinction. vLLM's contract is: `None` for EOS-via-primary-`eos_token_id` or length, a `str` when a `stop` string matched, an `int` when a token fired. **This study passes `stop=until` and no `stop_token_ids`, so a numeric `stop_reason` is *always* the model choosing to stop** — that is a sound invariant given the frozen config, and it should be written down as a comment rather than left implicit. Either add `stop_reason_is_token_id: bool` to the record, or decode the id to its token string so `"32007"` becomes `"<|end|>"` and lands in `_EOS_STOP_REASONS` naturally. Decoding reads better in the released artifact but needs a tokenizer inside `run_cell`, which currently has none; the boolean keeps `generate.py` tokenizer-free and is the smaller change. Either way the 1,699 existing records need the scoring-side rule below, so do both.

2. **Make the fallthrough non-silent — this is the part that matters.** Add an explicit numeric branch before the terminator check, and stop letting the final `return COMPLETE` mean two things:

```python
if stop_reason is not None and str(stop_reason).lstrip("-").isdigit():
    # A token id, not a stop string. This study passes `stop=until` and NO
    # stop_token_ids, so a numeric stop_reason is always an EOS-family token —
    # the model chose to stop. Recorded as its own route, not absorbed by the
    # catch-all: "unrecognised" and "complete" must never be the same answer.
    return COMPLETE
```

and then count anything still reaching the end. A `stop_reason` that is neither EOS, nor numeric, nor in `until` means the classifier does not understand its input — surface it in the report as `unclassified_stop_reason: N` and it will never take weeks to find again. **That counter is the general fix for the family B1 belongs to**, and it is worth more than either specific patch.
