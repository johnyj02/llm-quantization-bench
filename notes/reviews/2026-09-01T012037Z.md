## BLOCKER 1 — `compliance.HARNESS_UNTIL["bbh"]` drifted from `configs/tasks.yaml`; `TRUNC_STOPSEQ` is structurally zero for BBH at the chat level

`src/quantartifact/scoring/compliance.py:62`

- **Why it is wrong:** `configs/tasks.yaml:221` sets BBH's chat-level terminators to `["</s>", "Q:", "<|im_end|>"]` (corrected 2026-08-29, R18.1/R19.1). `compliance.py:62` hardcodes `"bbh": ("</s>", "Q", "\n\n")` — the **pre-correction, raw-level** set. `classify_termination` tests `stop_reason in HARNESS_UNTIL.get(task, ())`.
- **How it fails:** at the chat level the only non-EOS terminator that can fire is `"Q:"`. `"</s>"` and `"<|im_end|>"` are both in `_EOS_STOP_REASONS` and return `COMPLETE` at line 170. `"Q:"` is **not** in `HARNESS_UNTIL["bbh"]`, so it falls through to `return COMPLETE` at line 176. `"\n\n"` and bare `"Q"` are in the table but can never occur at the chat level — dead entries. **Result: every BBH generation cut mid-reasoning by `"Q:"` is classified `COMPLETE`, and `trunc_stopseq_rate` for BBH is 0.0% in every arm.** That is the §4 `TRUNC_STOPSEQ` differential-by-precision test, registered as confirmatory *before any generations existed* (prereg §11 category (a)). The paper would report "no stop-sequence truncation on BBH" as a measurement, not as an artifact of a stale literal. `arc_challenge_chat`, `gsm8k` and `gsm8k_cot` all match tasks.yaml correctly — BBH is the only broken one, because BBH's `until` is the one that got corrected.
- **The tests lock in the drift.** `tests/test_compliance.py:114,121,139,160` assert BBH `TRUNC_STOPSEQ` using `stop_reason="Q"` and `stop_reason="\n\n"` — the raw-level strings. **No test uses `"Q:"`.** The suite encodes the pre-R18.1 world and will keep passing.
- **The interface is the root cause.** `classify_termination(task, finish_reason, stop_reason, committed)` has **no `template_level` parameter**, and `until_by_template` gives BBH two different sets. For `template-v1`, which contains both levels in one run, the function cannot be right for both even in principle — and it has no way to tell them apart.
- **Confirmed by:** reading only — not executed. `configs/tasks.yaml:221-224`, `compliance.py:57-66,164-178`, `tests/test_compliance.py:114-163`; grep confirmed `until` appears nowhere in `records.py`.

## BLOCKER 3 — `"so"` is matched as a substring, so H2's conservative variant is systematically under-counted

`src/quantartifact/scoring/compliance.py:185,274-282`

- **Why it is wrong:** `_COMMITMENT_MARKERS` contains `"so"`, and `_appears_after_commitment_marker` does `lowered.rfind(marker)` with **no word boundary**, then takes `max()` across markers. `"so"` is a substring of `also`, `reason`, `reasoning`, `person`, `resolve`, `absolutely`, `consonant` — words that appear constantly in chain-of-thought text.
- **How it fails:** an incidental `"so"` inside an ordinary word pushes `last_marker` to near the end of the generation. `after_marker` then requires the gold to appear *after* that point, so it is almost always `False`. `conservative = (in_final_span or after_marker) and not already_extracted` therefore collapses to `in_final_span and not already_extracted`, and the `or after_marker` clause — half the pre-registered definition — is inert. `gold_in_trace_conservative` is **under-reported**, and the magnitude depends on generation length and vocabulary, both of which differ by arm. H2's headline is "how much of the 52% does an extractor recover?", which the docstring itself says "has to be airtight".
- **Confirmed by:** reading only — not executed.
- **Fix:** match markers with word boundaries — `re.search(r"\bso\b", lowered)` and similar for the phrase markers, handling `"\\boxed{"` separately since `{` is not a word character. A one-line change to build the marker positions from `re.finditer` instead of `rfind`.

## The design question

**The shared seam is right; the drift is in the parts that were *not* shared.** Three concrete cases, and each one is a finding above:

1. **`frozen_max_num_seqs` has four consumers and one of them is a copy.** It lives in `sm_pilot.py:96`, is imported by `sm_determinism.py:84` and `sm_reference.py:50`, and is **re-implemented verbatim** in `scripts/make_h8_tables.py:52-68`. The copy is the one that prints into the paper. Same shape as `HARNESS_UNTIL`: one value, two implementations, and the one furthest from the source of truth is the one the reader sees.

2. **`run_one_cell` is copy-pasted three times** — `sm_pilot.py:290`, `sm_reference.py:178`, `sm_template.py:152` — and has already drifted. `sm_reference`'s has `check=False`, the `__k{repeat_idx}` scratch tag, and reads `out_path` *before* unlinking (so a stale counts file restored from the checkpoint prefix can be read as this unit's result). `sm_pilot`'s has none of that and unlinks in a different order. Meanwhile `CELL_SCRIPT` **is** imported by reference, on purpose, and has not drifted. The evidence is right there: what is shared holds, what is copied moves.

3. **`sm_pilot.py` is a de facto library module that is also an executable.** `sm_determinism` and `sm_reference` import from it, which means importing it runs its module-level `SMOKE = ... or "--smoke" in sys.argv` — argv-sensitive state read at import time by two other entry points.

**Where I would draw the boundary:** move `frozen_max_num_seqs`, `CELL_SCRIPT` and one shared `run_cell_subprocess(payload, timeout)` into `src/quantartifact/` (a `stages.py`). Entry points then contain only their plan and their report. That is a mechanical move, no behaviour change, and it makes case 1 and case 2 unexpressible rather than merely currently-absent. Given the deadline I would not restructure anything else — the `records`/`generate`/`scoring` split is the right shape and should not be touched.

### Also fixed

- **Truncated gzip member (run-1 MAJOR 2, re-ranked toward BLOCKER).** CONFIRMED empirically:
  truncating a real 139 KB cell to half its length raised bare `EOFError` from BOTH
  `records.read_records` and `score_pilot.read_records`. `assert_cell_reusable` was in fact
  safe -- it reads only the first record, which always decompresses.
  Fixed with **opposite defaults per caller**, which is the substance of it: `read_records`
  now REFUSES by default (`TruncatedCellError`, naming the file and the recovered count),
  because silently returning a short cell gives every rate in it a wrong denominator. The
  resume path passes `tolerate_truncation=True`, because there a recovered prefix is exactly
  what should be skipped and the tail regenerated. Making both tolerant would have been the
  bug; making both strict would have made a killed job unresumable.
- **`until` RECORDED ON `GenerationRecord`** -- the reviewer's actual B1 recommendation.
  `SCHEMA_VERSION` 1.1.0 -> 1.2.0. `run_cell` stamps the list it passed to the engine, and
  `score_pilot` passes `record.get("until")` into `label_compliance`. `HARNESS_UNTIL` survives
  only as a fallback for records predating the field, and is now DERIVED from `tasks.yaml`
  rather than retyped. This is what makes the released artifact self-classifying (A24).
- **`--smoke` now exercises K=2 (run-1 MAJOR 4).** It excluded the path, so the mandatory
  rehearsal could not test the newest code in the stage. Smoke doubles one cell.
- **The K=2 completeness guard is no longer nested inside `if k2:` (run-1 MAJOR 1).** Nested,
  it caught PARTIAL drift and missed TOTAL drift -- every cell_id ceasing to match left `k2`
  empty, the guard unrun, and the job complete with no K=2 data and exit 0.
- **`--plan-only`'s reference figure (run-1 MAJOR 3).** Said 63,570 gens / ~10.5 h after K=2
  added ten doubled cells; now ~105,950 / ~17.5 h. This matters more than a docstring because
  `--plan-only` is what D10's confirmation is given AGAINST.

### One finding of my own, from the re-scoring

**`stop_reason` is sometimes a numeric TOKEN ID, not a string.** `32007` (Phi `<|end|>`, 1,227
records) and `151643` (Qwen `<|endoftext|>`, 472). `_EOS_STOP_REASONS` holds only string forms,
so these miss the EOS branch and fall through to the final `return COMPLETE`. The outcome is
correct but ACCIDENTALLY so, and it would misclassify if such an id ever appeared in an
`until` list. NOT yet fixed.
