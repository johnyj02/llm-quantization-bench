## MODERATE 2 — `not contrib.any()` is narrower than §9h's registered trigger

`src/quantartifact/analysis/interaction.py:206`

**Why it is wrong.** §9h registers the rule as applying *"Where the observed variance of the per-item contribution is exactly zero"*. `not contrib.any()` is True only when **every contribution is zero**. The bootstrap distribution is degenerate whenever all contributions are **equal**, which includes non-zero constants.

**How it fails.** If every item contributes exactly $+1$ — permissive fixes every item for the alt arm and none for bf16 — then `contrib.any()` is True, the bootstrap runs, every resample mean is exactly 1.0, and `np.percentile` returns `[100.0, 100.0]`. That is a **zero-width interval at +100 pp**, labelled `interval_method: "cluster bootstrap over items, 10000 percentile draws"`. It is the identical defect R25.1 exists to remove, on the same quantity, and §9h's own wording covers it. The most reachable version is **n = 1**: a single shared item makes the bootstrap degenerate regardless of the contribution's value, and a cell or BBH subtask with one paired item is not exotic.

There is a second half to this. `zero_variance_bound` returns a symmetric $(-h, +h)$ about zero, which is right for the all-zero case but wrong for an all-equal-nonzero case, where the bound must be centred on the point estimate. And `Effect.__post_init__` checks `ci_low > ci_high`, NaN, the p-value range and the ratio-null trap, but **does not check that `estimate` lies within `[ci_low, ci_high]`** — so a naive extension of the current helper to that case would silently emit an interval that excludes its own point estimate.

**Confirmed by:** reading only, not executed. I could not run `python -c` to demonstrate the `[100, 100]` output, so this is an analytic claim about `np.percentile` over a constant array. It is worth thirty seconds of your own verification before you act on it.

**Fix.** Two lines and one guard. Detect with `contrib.min() == contrib.max()` rather than `not contrib.any()`. When the constant is non-zero, offset the bound by the point estimate: `ci_low, ci_high = point + low, point + high`. And add `if not (self.ci_low <= self.estimate <= self.ci_high): raise` to `__post_init__`, which is the structural version of the check and would have caught either mistake.

**Reading it, the branch looks correct**, and to answer your three sub-questions directly:

- **`smf.gee(fixed, groups="item", data=frame, family=Binomial(), cov_struct=Exchangeable())`** is the right call shape. `GEE.from_formula(formula, groups, data, ...)` accepts `groups` as a column name, so passing the string works.
- **The `":" in name` filter picks exactly the interaction terms.** Patsy names two-factor categorical interactions `precision[T.gptq-4bit]:scoring[T.permissive]`, main effects have no colon, and no level name in this study contains a colon (arms, rungs and model keys all use hyphens and dots). Note that this is a **data-dependent** guarantee rather than a structural one: the `item` column is not in `fixed`, so its `|`-joined values never reach a coefficient name, but a future factor whose levels contained a colon would break the filter silently.
- **`exp(mean ± 1.96 * bse)` is the right interval.** Building the interval on the log-odds scale, where the estimator is asymptotically normal, and then exponentiating is correct and is what `conf_int()` would give; the alternative of `exp(mean) ± 1.96 * exp(mean) * bse` would be wrong. `bse` is the cluster-robust sandwich standard error by default, matching the clustering the bootstrap uses.

**One thing that genuinely strengthens R25.2(b) beyond what the ruling says**, and is worth recording: because `item` is keyed as `f"{model_key}|{task}|{subtask}|{item_id}"` **without the arm**, each cluster spans all arms, so `precision` varies within cluster. A conditional estimator such as `ConditionalLogit` would therefore keep it, but VB's conditional odds ratio is on a different scale from the marginal estimand, whereas GEE's population-averaged coefficient is on the same one. The exchangeable working correlation is knowingly misspecified here (two rungs of one arm are far more correlated than two arms, since the rungs re-score identical text), which does not bias the point estimate and is handled by the sandwich, so the "working correlation" wording in the unit string is honest.

**Two real defects in the branch.** First, **nothing checks `fit.converged`.** GEE with an exchangeable structure iterates, and statsmodels emits a `ConvergenceWarning` and still returns a result object; `GEEResults.converged` exists and is not consulted. A non-converged fit's params and bse go straight into the paper's odds ratio. That is the project's standing rule inverted: assert the fitter's reported state, do not assume it. Second, **`n=int(len(frame))` is a row count, not an item count**, while `interaction_marginal` sets `n=len(shared)`, an item count. The two effects sit adjacent in the H3 table with the same `H3_interaction_*` prefix, so a reader comparing `n=240` on the marginal against `n=2400` on the OR would conclude the odds ratio used ten times the data. `n_items` is in the context, but `n` is the reported column.

**Fix.** Raise on `not fit.converged` with the fitter and the iteration count in the message; set `n=n_items` and move the row count into the context; and add one test per fitter that actually fits a small frame and asserts the returned term names contain a colon. Given this is the paper's secondary registered estimator and has never run, that test is the highest-value one left in the package.

## Your questions, answered directly

**1. Is `zero_variance_bound` correct, and is the magnitude right at all four sites? Yes to both, verified.** The construction is the standard zero-events bound: Wilson's upper limit on 0 of $n$ is $z^2/(n+z^2)$, which bounds the rate of items that *could* have differed, and multiplying by the largest contribution a single differing item can make converts a rate bound into an accuracy-point bound. The guards on `n <= 0` and `max_abs_contribution <= 0` are right, and returning the method string alongside the interval is what makes the `interval_method` column trustworthy rather than a label applied by hand at the call site.

The four magnitudes:

| site | quantity | per-item range | magnitude | correct |
|---|---|---|---|---|
| `interaction_marginal` | $(\text{alt}_H-\text{alt}_L)-(\text{ref}_H-\text{ref}_L)$ | $[-2,+2]$ | 2 (default) | ✓ |
| `transitions.transition_effects` | $(n_{21}-n_{12})/n$ | $[-1,+1]$ | 1 | ✓ |
| `decompose.stopseq_differential` | $(b-c)/n$ | $[-1,+1]$ | 1 | ✓ |
| `interaction.rung_mcnemar` | within-arm rung gap | $[-1,+1]$ | 1 | ✓ |

Each of the three magnitude-1 sites also reproduces the pre-existing behaviour exactly, since the old local `proportion_confint(0, n)` with `[-high, +high]` was implicit magnitude 1, so the refactor changed no number that was already being reported. That is the right property for a consolidation and it is worth knowing you got it.

**2. Is the degenerate-case detection right? No.** See MODERATE 2. To answer your sub-question precisely: yes, there is a case with non-zero contributions that still has zero bootstrap variance, and your branch misses it — any constant non-zero contribution vector, of which $n=1$ is the easiest to hit. Your instinct in asking was correct.

**3. The GEE switch.** Reads correct on all three points you raised; see MODERATE 3 for the specifics and for the two defects that are not about correctness of the interval but about a non-converged fit and a mislabelled `n`.

**4. Anything I flagged before that you reintroduced.** One, and it is MODERATE 1. Everything else from the 2026-09-02 review is genuinely closed, and I checked rather than assumed: `null_value` now exists with a ratio-detection guard in `__post_init__` (CRITICAL 2), `_item_key` behaviour is confirmed by `interaction_glmm`'s `f"{model_key}|{task}|{subtask}|{item_id}"` (CRITICAL 1), `family` is now keyword-only on `holm_bonferroni`, `EXCLUDED_FROM_H3_INTERACTION` exists with `rung_mcnemar` deliberately taking no permission parameter, `stopseq_differential` records `termination_defined_at_rung` instead of accepting an ignored `rung`, and `stratum` now has `n_items_unpaired` with `fraction` returning `None` when it is non-zero plus a separate `fraction_of_paired`. The numeric `stop_reason` branch also landed with exactly the no-magic-numbers reasoning, citing the observed 1,227 and 472 record counts.

**5. `analyze_run.py`'s two limitations, and the reshaping.**

**Limitation 1 is worse than "degenerate", and the direction is what matters.** You describe the rung conjunction as degenerate, which is accurate but understates it in a specific way: because the single label is derived from strict *and* permissive jointly, `RECOVERABLE` already means "permissive found what strict missed", so replicating it across rungs makes the conjunction equivalent to "committed under permissive". A genuine per-rung conjunction over rungs 1 to 4 would additionally require commitment under *strict*, which is strictly harder. **So the stratum computed here is systematically larger than §1.1's definition, not merely differently defined.** §1.1 exists to buy conservatism, and R24.3 makes stratum size a first-class reported number, so a stratum biased upward is the direction that costs something. Second consequence: `decompose`'s `compliance_delta` reads `row["compliance"][rung]` and therefore returns a permissive-based commitment rate difference while `measured_strict_delta` is strict accuracy, so the H4′ identity mixes a rung-2 term into a rung-1 sum and inflates the `residual` for a reason that is not the general one the `residual` docstring gives. Both belong in the `limitations` list, which currently says only that the conjunction is degenerate.

**Limitation 2 is benign, and I can confirm it rather than just accept it.** With `until` absent, `classify_termination` falls back to the `tasks.yaml` union, and the union is *sound* rather than merely approximate: vLLM reports a stop string only when it actually matched, and the union can only add strings that were not in the request's stop list, so no false positive is possible. For `pilot-v2`, which is chat-level, only the chat terminators can appear and `"Q:"` is in the union. Your assessment is right and this one does not need escalating.

**The reshaping and the `cell_id` split are sound**, with one caveat worth a line in the docstring. `split("|", 1)` correctly handles `pilot-v2`'s R12.1 replicate cells (`qwen2.5-3b|awq-4bit-offload` yields an arm that matches neither `ALT_ARMS` nor `CONTRASTED_ARMS`, so every consumer skips it, which is the right outcome). But `sm_template` writes three-part cell ids (`model|arm|level`), so `--run-id template-v1` would produce `arm="gptq-4bit|chat"`, match nothing, and then fail loudly in `compute_stratum` on missing contrasted arms. That is fail-closed and therefore acceptable, but the guard checks only for the presence of a `|` while the docstring asserts a two-part shape; asserting `cell_id.count("|") == 1` would make the message name the real problem instead of surfacing it two functions later.
